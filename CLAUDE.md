## Safety rules for Phase 1

- **`/club` only exists when sample data is allowed** (`src/club/enabled.ts`): in development, or with `CCS_ALLOW_SAMPLE_DATA=1`, and never when `VERCEL_ENV=production`. Otherwise it answers "page not found".
- **The public website under `/site` is hidden the same way** (`siteEnabled` in `src/site/enabled.ts`, which follows `sampleDataAllowed`): visible while developing, in CI and on previews, "page not found" on production, including the page titles, so nothing about it leaks. Switching it on for the public at cutover (question D) changes `siteEnabled` only.
- **The "act as this test member" picker** is a test shortcut that exists only where invented data is allowed (`pickerEnabled` in `enabled.ts`, which follows `sampleDataAllowed`, not `clubEnabled`). Real people sign in by email link (step 6). When the member area is one day switched on for real members, the picker and the test outbox stay off because they hang off the sample-data switch, so that change is made in `clubEnabled` only. It is tested absent in a production setting.
- **Every permission check goes through `getCurrentActor()`** in `src/club/identity.ts`. Step 6 replaced what is inside that function (a real sign-in first, the test picker second) and nothing else: no page or handler changed how it asks.
- **Sign-in rules.** A sign-in link is made only for an address that can sign in, and the page never says whether one is; it works once, for a short time, and looking at it records nothing. The browser holds a long random secret that the database knows only as a fingerprint. Whether someone is still signed in is decided on every visit, so ending a household or removing an adult signs them out at once. The staff list (`CLUB_STAFF_LOGINS`) holds real addresses, so it lives only in private settings. `CLUB_SITE_URL` must be set wherever real email is sent, so a link can never be pointed at someone else's server.
- **Secrets stay in environment variables.** `CLUB_LINK_SECRET` (personal RSVP links) and `CLUB_IPAD_SECRET` (the front-desk iPad's private address) are both server-only, at least 16 random characters, never in code or in an address. Where the member area is switched off neither exists. Changing one switches off every address made from it. The real email sender's key (`RESEND_API_KEY`) is the same kind of secret: private settings only, never in code, a message, a log line or an error.
- **Never use `SUPABASE_URL` or the service key for club work.** Club code uses its own `CLUB_DATABASE_URL` (local or test databases only). The Postgres store (`createClubPool`) and the tests both refuse any database address that looks like Supabase. With `CLUB_DATABASE_URL` unset the member area runs on the in-memory sample.
- **What a public page may never show** (Grant, Oct 29): the bar, Happy Hour or drinks; access codes; staff phone numbers; iCrew links. The only phone number on a public page is the main line, (206) 622-0624. Pages under `/site` and the new homepage follow this. The current `/site` words do not yet: see "Public site refresh".

## What to keep from iCrew, and where to do better

Keep: members see what's free and book a boat or space themselves; booking windows and limits that stop one person hogging equipment; boats tied to skill levels; staff can take a boat out of service; multi-seat boats are booked as one outing.

Do better:
- One CCS-branded login and site, not a separate iCrew-branded app.
- Built for the whole club (rowing, fitness, social, spaces), not just a boathouse.
- Track whether a booking was actually used. iCrew only counts reservations.
- Keep a real record of when a household joins and leaves. iCrew has none.
- Rules are settings staff can change, not things a vendor configures.
- Every member and household gets a permanent internal ID from day one, with empty slots for QuickBooks, Brivo and Mailchimp IDs. (iCrew and Brivo share no ID today and match by name only.)

## Step 1: households and members (fake data only)

- **Household:** permanent ID, display name ("The Lindqvist household"), membership type (Resident = 33 and over, Intermediate = under 33, Non-Resident = lives farther away and visits rarely), status (active, or ended with an end date), join date, empty slots for QuickBooks ID and notes.
- **Member (one adult):** permanent ID, household, first and last name, email, phone, role (primary or additional adult), status, empty slots for Brivo credential ID, Mailchimp contact ID and future login ID.
- **Qualifications:** a member can hold rowing qualifications (sculling levels). Each records a level, who granted it, and when. Staff grant them; members can't give themselves one.
- **History:** a log per household of every change that matters (joined, member added or removed, type changed, membership ended), with date, what changed, and who changed it. The log can only be added to, never edited.
- **Ending a membership:** every member in the household is blocked from new bookings at once, and all future bookings are cancelled and logged. Past bookings stay as history.
- **Fake data:** about 14 invented households covering a single adult, couples, a three-adult household, each membership type, one ended household, one that joined this month, members with and without rowing qualifications, and one member whose email is shared with a partner. Invented names only; boat names come from `src/lib/shells.ts` when step 2 needs them.

## Step 2: bookable equipment and spaces, with rules (built Oct 22; in review)

One engine for everything bookable: Shell, Kayak, Paddle Board, Dock Space, Gym Space, Room Space, Work Space. Fully set up in the fake data: shells, kayaks, paddle boards, plus Dock Space to prove the engine is general.

Each item: name, type, seat count for boats (1 single, 2 double, 4 quad or four), qualification needed (if any), in-service or out-of-service status with reason and expected return date, and the rule set that applies. Rules attach to a type of item (for example "all singles") and individual items can override them.

Every number below is a **placeholder** until staff confirm real values (open question 5). Mark them as placeholders in the settings and on screen during testing.

| Rule | Placeholder value |
|---|---|
| How far ahead a member can book | 7 days |
| When new days open for booking | Midnight Pacific, a rolling window |
| Bookable hours | 5 AM to 8 PM (the club's member hours) |
| Time slots | 30-minute steps |
| Shortest and longest booking | 30 minutes and 2 hours |
| Future bookings one member can hold at once, per type | 2 |
| Bookings one member can have per day, per type | 1 |
| Latest time to cancel without it counting as a no-show | 2 hours before start |
| Gap between bookings of the same boat | 0 minutes (setting exists, off) |
| Qualification needed | Per boat class |

Behavior:
- **No double booking, ever.** Two requests for the same boat at overlapping times at the same moment produce exactly one booking. Enforced in the database (an overlap constraint), not only in the page.
- **Multi-seat boats:** the person booking owns the booking and adds other active members as crew. Each crew member must also be qualified. Crew don't count toward their own limits, but can't be in two boats at once.
- **Clear refusals** in plain language ("You can book up to 7 days ahead. Saturday opens Thursday at midnight."), never a bare error.
- **Cancelling:** members cancel their own bookings. Late cancellations are recorded as late.
- **Out of service:** blocks new bookings. Existing overlapping bookings stay; staff get a list of affected members.
- **Attendance:** every booking ends as upcoming, completed, cancelled, late-cancelled or no-show. Built in step 5: staff check people in or mark no-shows, and a booking nobody checked in for becomes a no-show by itself when it ends (see Step 5).
- **Staff override:** staff can book past the rules (for a lesson). Each override is logged with a reason. A test staff identity in the picker is enough for now.
- **Time zone:** store exact moments, show Pacific time. Clocks fall back on Nov 1, 2026; no lost or doubled slots that day.
- **Screens:** a day view by item (filter by type; members see "Booked" or "Yours"), a booking form that shows the rules and why anything is refused, and "My bookings" with cancel. Plain and functional, CCS fonts and colors, works on a phone.

### Step 2 as built

- **Rules are data.** `src/club/settings/booking-rules.json` holds every number (all marked placeholder) and the item classes (single, double, quad, kayak, paddle board, dock space). Rules layer: defaults, then the class ("all singles"), then the single item. `parseRuleBook` refuses typos and contradictions in words ("maxMinutes (100) must be a whole number of 30-minute slots"), so staff edits are caught by the tests. The database has matching tables (`booking_rule_defaults`, `item_classes`, `items`) so the staff screen in step 5 can edit the same data.
- **The engine** is `src/club/engine/bookings.ts`. `checkBooking` returns every reason a booking is refused, in a fixed order, in plain language, and marks which ones staff may set aside. `createBooking`, `cancelBooking`, `markAttendance`, `takeOutOfService`, `returnToService` do the work, each as one all-or-nothing change.
- **Facts versus rules.** Staff can book past the *rules* (window, hours, step, length, limits, qualification, gap) with a recorded reason, and the record lists exactly which rules were set aside. Staff can never set aside a *fact*: the slot is taken, the item is out of service, the time has passed, the member has left, nobody in two boats at once.
- **Time.** Every time is a real moment; days, hours and "midnight" are Pacific. Slots are stepped in real elapsed time, so Nov 1, 2026 (25 hours) has no lost or doubled slot and Mar 14, 2027 (23 hours) is handled. Late-cancel cutoffs count real hours.
- **No double booking, two layers.** The engine checks first and explains. The database (`club.bookings`, migration `20261023000000`) also refuses an overlap by itself with an exclusion constraint, and lines up competing requests for one item with a lock (without it, colliding requests stalled for about a second on a deadlock instead of getting a clean "taken").
- **Household link.** Ending a membership or removing an adult cancels their future bookings (not late; staff-cancelled), takes them off other people's boats as crew (the booking stays), leaves bookings under way and past ones alone, and writes it to the household's file. All in the same all-or-nothing change.
- **Screens.** `/club/book` (day view, filter by type, days in the window), `/club/book/new` (form that runs the real rule check and shows the rules), `/club/my-bookings` (staff see "All bookings"), `/club/equipment` (staff only: take out of service, return, see affected members).
- **The test clock.** `CCS_CLUB_NOW` (for example `2026-10-28T20:00:00Z`) freezes "now" for the member area, in development and tests only. It does nothing where the member area is switched off.

### The Postgres store (built Oct 22, after step 2)

- **What it is.** `PgClubStore` (`src/club/store/postgres.ts`) keeps the same `ClubStore` interface as the in-memory copy, so the rules engine did not change. With `CLUB_DATABASE_URL` set, `/club` reads and writes Postgres (a local or throwaway one only; hosted Supabase addresses are refused). With `CCS_ALLOW_SAMPLE_DATA=1` too, the invented club is loaded the first time, only if the database has no households.
- **How a change works.** Take one database-wide "writers" lock (shared by every app server), load the current records, let the engine change a working copy, write back exactly what changed, all in one transaction. Writers therefore take turns and always start from the truth. That is what makes a member's limits and "nobody in two boats" race-free (open question G, now answered), with the database's overlap rule still underneath as a second line of defence. Readers take a consistent snapshot and never wait for writers.
- **Rules and the database.** `booking-rules.json` is still the source of the rules; `syncRules` mirrors it into the rule tables on start-up so items can point at their classes. In step 5 the staff screen edits those tables instead.
- **What it loads.** All households, members, history, items and out-of-service entries, and bookings that ended in the last 90 days (`historyDays`). Older bookings stay in the database; the screens' "Past" list shows the last 90 days until a full-history view exists.
- **Never deletes.** The store refuses to delete anything and refuses to rewrite a history line. Bookings are cancelled by status, as in real life.
- **Proof.** The household, booking, household-plus-booking and daylight-saving tests run on both stores (the Postgres run needs `CLUB_TEST_DATABASE_URL`; CI always sets it). Extra tests check that Postgres holds exactly the same sample club as memory, that two app servers sharing one database cannot beat a limit, a slot or a "two boats" rule by racing, that the database overlap rule is translated into a plain refusal, and that the booking browser tests pass on a Postgres-backed server.

Not built yet, on purpose when this was written: the attendance-marking screen for boat outings and the staff admin screen (both now built in step 5), emails or texts.

## Step 3: fitness classes with chairs and a waiting list (built Oct 22; in review)

Grant's answers (Oct 22): the waiting list moves up **automatically and instantly**, first in line first; nobody can be **in two places at once** (two classes, or a class and their own boat, as booker or crew); a class **holds a gym or room space** (members cannot book that space while it runs); **no money** in step 3 (classes are included in membership; fees wait for the QuickBooks step). Assumed unless Grant objects: only staff create and change classes; members see just "full" and their own waiting-list place, never other names; classes have their own section next to Book rather than being folded into My bookings.

The building comparison: a class session is a scheduled use of the clubhouse room. The chairs are its unit count; the waiting list is the applicant queue; a sign-up is a lease on one chair for one evening.

- **Pieces.** A *class* ("Morning Yoga": usual chairs, length, room, instructor, optional own rules). A *session* is one dated occurrence with its own number of chairs, and it holds its room. A *sign-up* is one name on one session's sheet: `enrolled` (has a chair), `waitlisted`, or how it ended: `cancelled`, `late_cancelled`, `attended`, `no_show`.
- **Rules are data.** `src/club/settings/class-rules.json` (placeholders, like the boat rules): sign-up window (14 days, opens at midnight Pacific), closes 30 minutes before, leave without penalty until 2 hours before, the automatic move-up runs until 2 hours before, waiting list up to 10, 5 upcoming places at once (a waiting spot counts), 1 class a day. A class can override any of them under its own `rules`. A typo is refused in words by `parseClassRules`.
- **The engine** is `src/club/engine/classes.ts`: `checkSignUp` (every reason in plain words, read only), `signUp`, `leaveClass`, `markClassAttendance`, `createClass`, `planSessions` / `scheduleSessions` (single or weekly; weekly keeps the same Pacific clock time across the Nov 1 and Mar 14 clock changes), `cancelSession`, `setCapacity`, `sessionView`, and `classLedger`. `engine/ledger.ts` combines it with the boat ledger as `clubLedger`: ending a household or removing an adult now also takes them off future classes (not as a late cancellation), moves the waiting lists up behind them, and writes `signups_cancelled` to the household's file.
- **The waiting list.** A chair freed by someone leaving, by more chairs, or by a member leaving the club goes to the first person waiting, in the same all-or-nothing change. After the move-up cutoff (2 hours before) a free chair goes to whoever asks first, and someone already waiting can take it. Order is the order names were written (database `seq`), so someone who leaves and comes back goes to the end.
- **Facts, not rules.** Unlike boats, staff **cannot** set aside class rules for one member: they raise the chairs instead. Reason: a sign-up has no room in its record for an override reason, and "add a chair" is the honest tool. Grant confirmed this Oct 22 (open question L).
- **One place at a time.** A chair *or* a waiting spot holds the person's time. Booking a boat is refused if you (or your crew) are in a class then (`in_class`); signing up is refused if a boat is booked then (`boat_busy`) or another class overlaps (`person_busy`). A class holding a room makes `checkBooking` refuse that room (`room_in_use`), for staff too.
- **The database enforces** (migration `20261025000000_club_classes.sql`, tested against a real Postgres): chairs never over-filled, a room never used by two classes or by a class and a booking at once (one lock per room shared by both checks), one live line per person per session, sign-ups only move forward, a session cannot be moved or revived, chairs cannot drop below the people in them. Each rule was broken on purpose to prove a test notices.
- **Screens.** `/club/classes` (pick a day, see chairs left, your place), `/club/classes/[sessionId]` (the rules in words, why a sign-up is refused, sign up / join the waiting list / take a free chair / leave; staff also see the sheet and names, mark attendance, change chairs, cancel the class and see who to contact), `/club/my-classes`, and for staff `/club/classes/manage` (add a class, schedule one date or a weekly run, with every clash explained before anything is saved). The `/club/book` day view shows a room held by a class as "Class".

## Step 4: events and RSVPs (built Oct 23, reworked the same day; in review)

- **Spots.** The member and each guest take one spot. The limit counts people, not RSVPs. A *party* is the member plus guests (the screen says "party of 3"; the database still stores `guests`, the party minus the member). - **The database enforces** (migration `20261026000000_club_events.sql`, tested against a real Postgres): an event with a limit never has more people going than the limit (member plus guests), a name is on a list once, an RSVP only moves forward, a cancelled event stays cancelled, the limit cannot drop below the people going. `club.end_household()` is replaced again to cancel future RSVPs too. ## Editing a person's details (built Oct 23; in review)

- **The file.** A CSV (what a spreadsheet saves as "CSV (Comma delimited)"). A household whose QuickBooks ID is already taken is refused by the engine as well.
- **The screen.** `/club/admin/import` (a link in the Staff office's tools), staff only (a member gets "page not found", someone signed out is asked to sign in). A file box, **Check the file** (shows the problems, or the preview), and **Add these households** which only appears for a clean preview. The preview lists up to 50 households with their adults and says "...and N more" past that. Changing the file clears the preview, so the Add button never belongs to a different file. The two buttons are one server action (`importRoster`), which checks the member area is on and the person is staff before reading the file, and refuses an Add that does not carry the fingerprint and the counts of a check (plain digits only). After adding, the page says how many households and adults were added.

Out and In differ from the booked times on most rows, but Grant says treat them as the booked times (open question BL).
- **A store of its own.** `HistoryStore` (`store/history.ts`, with `MemoryHistoryStore`; `store/history-postgres.ts`, with `PgHistoryStore`; `store/history-instance.ts`) is **not part of `ClubState`**, because a year is about 27,000 rows and every page reads the club's records on every visit. - **The reader** is `engine/icrew.ts` (`readIcrew`). It finds columns by name in any order (case, spaces and punctuation ignored), reports **every** problem at once with spreadsheet row numbers (the first 200, then "...and N more"), and keeps only days that have **passed** (today and later days are left out with a notice, because those bookings can still change in iCrew). Times become real Pacific moments (`pacificWall`), so Mar 8 and Nov 1, 2026 are exact; `12:00am` as an end time is the end of the day. A row with no `ItemType` is called `Event`. A booking is stored once however many files mention it: its key is a fingerprint of iCrew's ID plus the person it is for (an event shares one ID across people, so the person is part of the key). The template (`/api/club/history/template`) has three invented example rows that the reader refuses (`EXAMPLE-1`...). Limits: **4 MB** (just under Vercel's 4.5 MB request cap; `next.config.ts` raises the server-action body limit from 1 MB to 5 MB for this) and 60,000 rows; a bigger export is uploaded in pieces.
- **Names, not accounts.** iCrew has no emails, so a booking carries the names it was written with plus a **key** (`engine/people-names.ts`: lower case, no accents or punctuation, only the first and last word, so a middle name, "Jr." or a nickname in brackets does not stop a match). A joint booking names both people (the first borrows the last name written after the second). **Matching happens when someone asks, not when the file is added**, so a name that matched nobody can match later (after an email or name is corrected) and nothing goes stale. A key held by **more than one member (counting people who have left) matches nobody**: that member is told to ask staff, and staff can still find the bookings by name. ## Resignations: ending memberships from a file (built Oct 27; merged as PR 34)

Grant's answers (Oct 27): resignations (open question AX) came next, ahead of the real email sender and the cutover tools; **6 to 20 households resign in a typical month**, so a bulk tool is worth building; the list is **a file staff upload** (upload, read-back, confirm, the pattern of the roster import); and a resignation **takes effect right away, when staff confirm**. Not chosen, so not built: a "who's missing" report that compares a fresh QuickBooks list to the club and ends nothing; ending on a date staff pick; entering a resignation dated to a past day. In the same round Grant answered BL: Out and In stay as the booked times.

The building comparison: move-out day. The office gets a list of units whose tenants have given notice (from QuickBooks, from the board, from wherever staff trust). The clerk first gets a read-back ("9 leases would end today; 23 bookings, class places and RSVPs would be cancelled; row 4 names a unit that does not exist"), and only when the list is clean does the clerk end them all at once, each exactly as at the front desk. Nobody is added or changed, and a lease that already ended is skipped.

- **The file.** A CSV, one row per household. Columns, found by their names in any order, spaces and capitals ignored: **QuickBooks ID** (required), **Household name** (optional but strongly recommended) and **Note** (optional: why they left, kept in the household's file). Extra columns are ignored and mentioned. Dates in the file are not used: households end the day staff press the button, and the page and the read-back say so. The blank template (`/api/club/resignations/template`, staff only) holds two invented example rows, and the tool refuses them (`EXAMPLE-1`, `EXAMPLE-2`). Limits: 200 KB and 1,000 rows. An Excel file, a file with a stray binary character, an empty file and a quotation mark that is never closed are each refused in words.
- **The reader** is `engine/resignations.ts` (`readResignations`) over `engine/csv.ts`. It changes nothing and reports **every** problem at once, with row numbers as a spreadsheet shows them (the header is row 1): an empty ID, an ID over 100 characters, a template example row, a name over 120 characters, a note over 200, and a QuickBooks ID listed twice. A completely empty row is skipped.
- **The read-back** is `planResignations(state, text, now, rules)`, which changes nothing. **Problems** (nothing can be ended while there is one): everything the reader found; a QuickBooks ID no household has (with the hint that a spreadsheet can drop a leading zero and that a household with no ID is ended in the household desk); a Household name that is not the name on file (compared ignoring capitals and spacing), so a mistyped ID can never end the wrong household; and more households than `maxHouseholdsPerFile` (households that are skipped do not count). A household that has **already ended is skipped** and listed. **Notices** (they do not stop it): ignored columns; no Household name column; a file that would end `warnPercentOfActive` percent or more of the active households ("if you meant to upload the whole roster, stop here"); and a standing note about dues (the file's dates are not used, the households end today, no dues are billed from the next month on, and months already started are billed as usual when closed along with anything not yet billed). What ending them **cancels** is worked out for **all the leaving adults together** (`departurePreview`), so a boat booked by one resigning household with crew from another is cancelled once and the read-back names exactly what the run then cancels.
- **The run** is `runResignations(store, ledger, ctx, text, expect?, rules?)`: staff only, and one all-or-nothing change under the writers lock. It reads the file again inside the change, refuses a file with problems, refuses when there is nothing to end ("Every household in the file has already ended, so there is nothing to do."), and refuses when the file or the club no longer matches what staff previewed (a fingerprint of the exact file plus the household and adult counts they saw). Then it ends each household in file order through `endHouseholdRecords`, the same code the household desk uses (`endHousehold` is now a thin wrapper around it, so there is one way to end a household): the adults are blocked and signed out, future bookings, class places and event RSVPs are cancelled, the waiting lists move up behind them (also across households that are both leaving), and the household's file gets its lines. The `membership_ended` line reads "Membership ended on Oct 28, 2026, from a resignations file. 3 adults can no longer book. Note: Moved away", with the source and note in its details. Two staff pressing confirm at once end the households once. A failure part-way ends none of them. A test holds the result to ending the same households one at a time: the same records, on both stores.
- **Rules are data.** `src/club/settings/resignation-rules.json` (placeholders): `maxHouseholdsPerFile` 50 and `warnPercentOfActive` 25. `parseResignationRules` refuses a typo, a missing key and a silly number in words. They only guard against uploading the wrong file (for example the whole roster); they do not decide who resigns.
- **No migration.** Ending a household already goes through the database's existing rules (the household's file lines, the adults, the bookings cancelled by status), so there is nothing new for the database to enforce.
- **The screen.** `/club/admin/resignations` (a "Resignations" link in the Staff office's tools), staff only (a member gets "page not found", someone signed out is asked to sign in): instructions, a file box, **Check the file** (the problems with their rows, or the read-back with a card for each household, the notices, "What it will cancel" using the household desk's own preview view limited to 50 lines a list, and the households skipped because they had already ended) and a red **Yes, end N memberships** button that only appears for a clean read-back. The two buttons are one server action (`endHouseholds`), which checks the member area is on and the person is staff before reading the file, and refuses an end that does not carry the fingerprint and the counts of a check (plain digits only). Changing the file clears the read-back. After ending, the page says how many households and adults, and how many bookings, class places and event RSVPs were cancelled.
- **Hidden like everything in `/club`.** The page, the template and the action are "page not found" on the live site; `club-hidden.spec.ts` covers all three (the action called with its real ID from the build).
- **Not built, on purpose:** a "who's missing" report; ending on a chosen future date (the system would have to end memberships by itself on that day); back-dating a resignation; undoing an ending (a household that comes back is a new household, question A); telling the household or the board (no email sender yet); changing anything but ending.

- **Proof it can fail:** this step was broken on purpose 96 ways and each run showed whether the tests noticed: the file reader (20), the read-back (19), the run (14), the shared ending code (8), the rules checker (5), the server action (9), the screen, its template and the Staff office link (11), the shared preview component (7) and the live-site checks (3). 91 were caught the first time. ## The real email sender (built Oct 27; merged as PR 36)

- **Who sends** (`getMailer` in `auth/mail.ts`): where invented data is allowed (development, previews, automated tests) it is **always the test outbox**, even when Resend's settings are present, so a test build can never email anyone. No key means no real sender. A key with a missing or wrong companion is **refused in words** (`MailSettingsError`), the sender then stays off, and the words are logged once per server (never on every page view). **No message, log line or error ever holds the key.**
- **The sender** (`auth/resend.ts`, `createResendMailer`): one POST to `https://api.resend.com/emails` per email with the key as a bearer token, the From line, one recipient, the subject and the **plain text** (no HTML) and `reply_to` when replies are on. A failure (no answer, a refusal, an unreachable service) throws a short message with Resend's status and reason, with the key and the recipient's address scrubbed out because messages end up in logs. The sign-in treats a failure like it always has: it looks the same from outside (`"ignored"`), and the log line is the only trace.
- **The test command** (`auth/send-test-email.ts`): `npm run mail:test -- you@example.org` sends exactly one test email through the same sender code, reading the same three settings from the environment or `.env.local`. It prints where the email went, what the From line was and where replies go, or why it could not send (a missing key, a wrong setting, Resend's own refusal with the usual causes: the domain not verified, a From address off that domain, a key from another account). It exits 0 sent, 1 could not send, 2 used wrongly. To let Node run these TypeScript files directly, `tsconfig.json` now has `allowImportingTsExtensions` (no effect on the build, which type-checks only) and the files this command loads import each other with their `.ts` endings. The file runs the command only when it is the program being run, never when a test or the website loads it.
- **Go-live items (not code):** create the Resend account under the CCS-owned shared email (question E); the club's domain is held by someone else (Grant, Oct 25), so the DNS records Resend gives (sender verification and anti-spoofing records) go to them; choose the From address; **switch off link and open tracking for the domain in Resend**, because a tracked link goes through Resend's servers first and the one-time secret is in the address it rewrites (the test command says so too); set the three settings and `CLUB_SITE_URL` in Vercel's Production settings only; run `npm run mail:test` to a staff address and check the spam folder; and plan for Resend's Pro plan around cutover, when everyone signs in at once (the free plan stops at 100 emails a day).
- **Not built, on purpose:** any email other than the sign-in link (waiting-list move-ups and event changes N, T and X; a note to the person whose email address was changed AK; a note to a household whose membership ended); retries or a queue; bounce, complaint or delivery tracking; HTML emails or the club's branding in them; a check that the domain is verified (Resend says so at send time); a staff alert when sends start failing (question BP); and anything on the live site: no new page or address exists, so nothing here can be seen from outside.
- **Proof it can fail:** this was broken on purpose 56 ways and every one was caught the first time (the checks were run unbroken first and passed): the settings checker (20: no key not meaning "no sender", a loosened key shape and length, a missing From not refused in its own words, the default reply address drifting from the public page, the word `none`, a blank reply setting, an unchecked reply or From address, the name limit loosened or off by one, control characters, quotation marks and @ signs allowed in a name, brackets with no name, text after the closing bracket, untrimmed values, a message that repeats the key), the Resend sender (20: wrong address, method, authorization scheme or user agent, the recipient not a list, `reply_to` always sent or misnamed, HTML sent too, the key added to the body, the From line ignored, no timeout or a ten-times-longer one, a refusal or a redirect counted as sent, the key or the address not scrubbed from a message, a long reason not cut, a timeout not recognised, Resend's reason dropped), the chooser (7: the test outbox no longer winning in a test build, the area switch ignored, either default switch forced, a bad setting logged every time, the real sender never made) and the test command (9: the command never running, wrong exit codes, two addresses accepted, an address not checked, a missing key not stopped, sending to the wrong address, a wrong success line, the causes line on the wrong stream). **Two things were not done and are said plainly.** A browser-level breakage of "the test outbox wins in a test build" was not run, because it would have sent a real request to Resend's servers (with a fake key); the unit tests catch that breakage, and the browser tests carry fake Resend settings on both member-area servers (in-memory and Postgres), so every sign-in browser test would fail if a test build ever chose Resend over the outbox.
